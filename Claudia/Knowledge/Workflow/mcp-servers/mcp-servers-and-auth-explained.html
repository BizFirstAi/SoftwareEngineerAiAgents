01

What MCP is here

MCP (the Model Context Protocol) is a standard wire format that lets an LLM-driven conversation call out to external tools — plain functions with a name, a description, and a JSON-Schema parameter list — mid-conversation, over a client/server connection, the same way it would call any native function.

The difference is only where the implementation lives. A native function runs in the same process as the conversation. An MCP tool runs on the other end of a connection instead — sometimes that's a genuinely separate program (GitHub's own MCP server, spawned as a subprocess), and sometimes it's just a different C# project loaded into the same running platform server. From the LLM's point of view the two are schema-indistinguishable: they land in the exact same function list, dispatched through the exact same executor factory. MCP is an interface choice, not a statement about deployment topology.

"Merged into the platform server" means one specific thing, confirmed explicitly during the build: only where the MCP endpoint is hosted changed. Each tool module's code was never moved, copied, or collapsed into the platform server project — it stays its own class library with its own Single-Responsibility boundary, and the platform server only takes a ProjectReference to it and chains one more .WithToolsFromAssembly() call onto the same builder. A standalone gateway process (BizFirst.Ai.Mcp.Gateway) was built first and proved the pattern, then retired in favor of this shared hosting once the memory cost of running a second full ASP.NET Core process — duplicate DI graph, duplicate DB connection pool — stopped being worth it on a memory-constrained dev box.

03

How a call actually flows

A tool call is not decided by anything MCP-specific — it's an ordinary LLM function-call decision. What differs is everything downstream of that decision.

1 MCPToolAgentHook On every agent load, calls the live tools/list on each of the agent's granted MCP servers and merges the results into agent.SecondaryFunctions — the same list native functions sit in.
→
2 FunctionExecutorFactory Matches the LLM's chosen function name and routes to McpToolExecutor — one factory, no separate "MCP mode" in the conversation loop.
→
3 McpClientManager Opens or reuses a cached client connection (keyed by server ID + credential), substitutes any {fieldName} credential wildcards, and calls the SDK's CallToolAsync.
→
4 [McpServerTool] The real C# tool method (e.g. AddFormControlTool), attribute-generated schema, DI-resolves its backend service as a plain parameter.
→
5 IFormsExtendedService … The real backend service — same one a controller action would call — executes in-process. No HTTP hop for any first-party module.

Two details matter for everything in the next section. First, tool schema is always discovered live, at agent-load time, against the running server's own tools/list — the database's AIMCP_McpTools.Schema column is never read to build what the LLM sees; it only works as an optional per-agent name allow-list, letting one agent see a curated subset of a server's tools while another sees all of them. Second, credential resolution already follows this codebase's mandated pattern end to end — a three-tier chain (a Flow Studio satellite override, then the server's own default, then the calling agent's own default) resolves a real, vault-decrypted secret and substitutes it into ConfigJson's wildcard tokens at connect time. That part of the story was solved before any of this MCP work started; the open problem is a different one — identity, not credentials.

04

The authentication story

Every write route these tool modules wrap — [AuthorizeTenantAdminAttribute], [AuthorizeRegularUserAttribute] — is decorated the same way the equivalent REST controller action already is. The question that actually needed answering wasn't "which role is required," it was much more basic: does that check ever run at all on an MCP call?

The gap that was found

AuthorizeTenantAdminAttribute and AuthorizeRegularUserAttribute are ordinary ASP.NET Core ActionFilterAttributes. They only execute when a request is dispatched through MapControllers()'s MVC action-invocation pipeline. But per the call flow above, every MCP tool method calls its domain service (IFormService, ICredentialService, …) directly, as a plain DI parameter — deliberately, to avoid an internal HTTP hop. The consequence: when the first two write-capable modules shipped, their write tools carried zero authorization check of any kind — not mis-scoped, structurally unreachable. The only thing touching identity on the /mcp path was a fixed SetBackgroundJobContext(tenantID: 1, …) call, and that call was never doing authorization work — it only decided which tenant's rows got written and stamped. Every MCP-visible write tool could be called by anything reaching the endpoint, landing under Tenant 1, with nothing checking whether the caller was entitled to call it at all.

The fix design settles on three trust tiers, because "who is calling" turns out to be three genuinely different shapes of caller, each needing a different answer.

Tier B is the one worth reading carefully, because "built" understates it. The claims-construction half landed and build-verified: McpAgentTenantResolver looks an agent's real TenantID up directly against AIAgent_Agents — bypassing the normal tenant-scoped repository path, which needs a tenant to already be known, exactly what this call is trying to establish — and the /mcp middleware now constructs a real ClaimsPrincipal instead of leaving HttpContext.User untouched. But nothing on the actual tool-call path reads that principal yet. Tool methods still call IFormService/ICredentialService directly, bypassing MapControllers() entirely — so AuthorizeRegularUserAttribute still never executes for a real MCP call today. The fix put a passport in the traveler's pocket before building the checkpoint that reads it. The design for that checkpoint is a single shared guard every [McpServerTool] method passes through — not a re-route through controllers, which would reintroduce the HTTP hop the whole in-process design exists to avoid — but it hasn't been built.

Reserved for humans, deliberately

create_mcp_server, create_agent, and create_credential are excluded from both Tier B and Tier C by design, not just by role string. A newly-registered MCP server's stdio command or SSE endpoint becomes something a future agent's own tool-calling can reach — the single highest blast-radius action in the whole catalogue; a new agent can be granted access to any MCP server, and a new credential can be pointed at anything. Tier B's build already made the conservative call — AuthorizeTenantAdminAttribute was deliberately never extended to accept McpAgentWriter — and that conservatism is meant to hold permanently for these three, not as a placeholder pending a future relaxation. Cross-tenant calling sharpens the reasoning rather than changing it: a same-tenant compromised agent is at worst bounded to its own tenant's data; a leaked or over-scoped cross-tenant key is not bounded by tenant at all, which is exactly the shape of failure these three tools cannot be allowed to have.

A tenant is not just a number

Tier C's design leans on apiKey.TenantID to say which tenant a cross-tenant caller belongs to — but this codebase has already been burned by treating a bare numeric tenant ID as sufficient identity. The AI-agent-definition cache hit exactly this bug: keyed on the agent ID alone, with no tenant or environment in the key, two tenants sharing the same numeric ID could collide within the cache window. Its fix keys on TenantSlug + Environment + TenantID together, because the same numeric TenantID is not guaranteed unique across environments or slugs — a tenant provisioned twice, once per environment, can legitimately carry the same number in both. The same discipline has to carry into Tier C's enforcement guard: apiKey.TenantID alone is not a safe caller identity to gate a cross-tenant write on unless it's read alongside the same slug-and-environment context, or two different environments' identically-numbered tenants become indistinguishable to the exact check meant to keep them apart.

Why extend IAM_ApiKeys instead of building real OAuth 2.1. The official MCP authorization specification is unambiguous about the shape it expects: an MCP server acts as an OAuth 2.1 Resource Server, Authorization Code plus PKCE for a human-delegated flow, and client_credentials-grant OAuth as its own named answer for a non-interactive, machine-to-machine caller. But the spec is equally explicit that authorization is optional — a server that doesn't implement it isn't out of spec — and it tells STDIO transports specifically to use environment-provided credentials instead, not OAuth.

What real production MCP servers actually ship confirms that optionality is exercised, not theoretical. Stripe's own MCP server prefers OAuth but documents a restricted, scoped API key as a fully first-class Bearer-token alternative when a client doesn't support OAuth. GitHub's official MCP server lets a fine-grained Personal Access Token take precedence over OAuth outright. Cloudflare's guidance centers OAuth for user-delegated access but separately documents API tokens as the correct mechanism for CI/CD and automation callers. The pattern across all three is the same: OAuth for interactive, user-delegated access, and a scoped, revocable API key as a permanent, non-deprecated alternative for server-to-server callers — not a stopgap on the way to OAuth-only.

This codebase has no OAuth Authorization Server anywhere to extend — building one (dynamic client registration, PKCE verification, token and metadata endpoints, audience binding) is multi-week new infrastructure and a new attack surface, for a caller shape the industry's own real examples already treat API keys as the right tool for. IAM_ApiKeys is real, live, and has already been extended for this exact "external caller, no JWT, tenant-scoped key" shape twice — once for the Knowledge API, once for ChatDesk's anonymous widget. A third extension, scoped to MCP with its own grant strings and its own AIMCP_McpApiKeyServerGroups join table reusing the same tool-visibility mechanism agents already use, is the same pattern a third time — not a new one.

05

Why not RAG for workflow & node config

Atlas Forms leans on retrieval-augmented generation — a vector-searched reference corpus an agent queries at need. Workflow and node configuration, built right after it, deliberately does not. The reason isn't that one module is more sophisticated than the other; it's that RAG is the right tool for one kind of source material and the wrong tool for another.

Retrieval earns its cost when the true source is large, unstructured, and scattered — something no single turn can hold, so an agent has to search for the relevant slice. It's the wrong tool when the source is already one structured row you can look up directly by key.
SubstrateAtlas FormsWorkflow node config
Source of truth 88–115 control types, known only as frontend TypeScript — no backend representation at all Process_ProcessElementTypes.ConfigurationSchema, a populated JSON-Schema column, one row per node type
Why it went this way Nothing structured to look up server-side — had to be authored into a two-tier, vector-searched reference corpus Already structured and DB-resident — a two-tier direct read (overview list, then on-demand full schema) does the same job with no vector store
Known caveat Compact "always-loaded" tier runs ~4× over its original token budget at full coverage At least one sampled type's seeded schema is confirmed stale against its real settings class — a data-quality problem to audit, not a reason to reach for RAG

The same reasoning extended to the smaller, cross-cutting concepts an agent also needs — expressions, guardrails, node policies. All three behave identically regardless of which of the ~107 node types hosts them, and all three together amount to roughly 1,300 lines across eight markdown files: small and structure-agnostic enough to curate into one static reference tier rather than stand up a second retrieval pipeline. A vector-backed fallback tier is reserved, not built, for the rare node type whose configuration proves irreducibly too complex for a single JSON-Schema column to describe.
