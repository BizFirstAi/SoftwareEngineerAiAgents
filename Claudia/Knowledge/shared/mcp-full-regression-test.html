Real bugs found and fixed this pass (App Studio Player UI verification)

Bug 1 — App Player bare-root URL rendered no content

Symptom
http://localhost:6130/1064?tenantID=1&token=... (bare root) rendered only the nav bar — the Michael Jackson biography content was completely missing — while http://localhost:6130/1064/page/home?tenantID=1&token=... (page-anchored) rendered correctly.
Root cause
RouteResolverService.resolveFromUrl() had no fallback branch when no URL pattern matched (unlike its sibling resolve(), which falls back to paneWidgets.find(w => w.isDefault) ?? paneWidgets[0]). A bare app-root request matches none of the widget/{id}, page/{slug}, or custom-routeTemplate branches, so it fell through to `return null`, leaving AppEngine.loadApp() never calling applyRouteTarget() — the primary content section's renderedWidgets entry was never populated for the page-scoped Home content.
Fix
packages/app-handlers-generic/src/services/RouteResolverService.ts — resolveFromUrl()'s terminal `return null` now delegates to `this.resolve({})` (the same fallback resolve() already has), and sets the URL segments from that fallback target.
Verified
Both http://localhost:6130/1064?... and http://localhost:6130/1064/page/home?... now render "The King of Pop" body content identically. Screenshot: C:\Users\binoy\AppData\Local\Temp\claude-chrome-screenshots-NQqYN0\screenshot-1789067131510-50.jpg

Bug 2 (found while verifying Bug 1) — 124 stale compiled files silently shadowing live TypeScript source

Symptom
The Bug-1 fix, verified correct by reading the file, did not take effect in the browser even after killing and restarting the app-player dev server with node_modules/.vite cleared. Adding a debug marker, and then a deliberate `throw`, at the very top of resolveFromUrl() had zero effect on the running app — proving the browser was not executing this file at all.
Root cause
104 compiled .js/.d.ts/.js.map/.d.ts.map files (dated 2026-09-04, six days stale) were sitting directly inside app-studio/packages/app-handlers-generic/src/ next to their real .ts/.tsx sources — plus 20 more in bizfirst-common/app-studio-player/src/. All are gitignored build byproducts (src/**/*.js, confirmed via `git check-ignore`), left behind by an earlier in-place `tsc` run that emitted output alongside sources instead of to dist/. AppEngine.ts imports RouteResolverService via the literal specifier './services/RouteResolverService.js' (standard TS/Node16-style ESM); Vite/Node resolves an explicit .js import to an actually-existing .js file on disk before ever falling back to transpiling the sibling .ts — so the ENTIRE app-handlers-generic + app-studio-player module graph had silently been running 6-day-old compiled code all night, shadowing every edit made to these two packages' real sources in this and possibly earlier sessions.
Fix
Deleted all 124 stray compiled artifacts (confirmed gitignored and each had a matching .ts/.tsx sibling before deletion). Vite's already-transformed-module cache still had the deleted files' resolved import paths baked in (a mid-session reload produced transient 503s on the now-missing .js URLs), so the dev server was fully killed and restarted with node_modules/.vite cleared to force a clean re-resolution.
Verified
Network trace after restart shows AppEngine.ts and RouteResolverService.ts (not .js) being fetched and executed; the Bug-1 fix now takes effect (see Bug 1's "Verified" line above).
Follow-up recommended (not done this pass — out of scope, broader repo sweep)
This same "tsc output committed/left alongside src" pattern may exist elsewhere in the BizFirstAiStudio monorepo — a background scan of the rest of src/ for the same shadowing pattern was kicked off but not reviewed before this report; worth a deliberate, separate cleanup pass with review rather than a blind repo-wide delete.
