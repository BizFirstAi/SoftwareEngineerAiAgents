Methodology · applies to every node type

Testing a node you can't click on

A workflow execution node has no screen of its own — it only does something once it's wired into a real Flow Studio workflow and run. This is the playbook for testing one anyway: for real, with real evidence, without guessing at credentials you were never given.

Scope: every Octopus / Flow Studio execution node type Worked example: Elasticsearch Companion doc: 02-guidelines.md — the step-by-step bootstrap procedure

What is a "node," exactly

The building block, not the building

A node type is a registered entry in Process_ProcessElementTypes — a row with a Code like elasticsearch, http-request, or sql-server — paired with a real C# executor class under BizFirstPayrollV3\src\mvc-server\AI\ExecutionNodes\. It is what a user drags onto a Flow Studio canvas: one shape, one config form, one job.

It is not a React app. It has no URL of its own, no page to open, no login screen. The only way to see it do anything is to wire it into a real workflow — a trigger feeding it, its output going somewhere observable — and execute that workflow for real. Every convention in this framework exists because of that one fact.

01

Registry row

Confirm it live in the DB, not just present as an unapplied script — Process_ProcessElementTypes.Code.

02

Real executor

A C# class that actually registers itself and routes execution — not a stale or duplicate folder sitting nearby.

03

Config schema

What its Atlas Form asks for, cross-checked against what its code actually reads and validates at runtime.

Why this exists

Manual verification doesn't scale, and neither does trusting a claim

Dozens of node types ship across this platform. "It compiles" and "the form looks right" are not the same claim as "it actually executes and does the right thing against a real external system." This framework closes that gap the same way its sibling, agentic-testing\, closes it for React apps: an agent builds real test cases, runs them for real, and writes down exactly what happened — Pass, Fail, or honestly Blocked — with evidence a human can check afterward instead of a summary they have to take on faith.

What "resources" means for a node

Four things every resource.md must cover

  1. Prior-reviewed DB-side work. A node-engineer pipeline usually already built and validated this node's Atlas Forms, DataTemplates, and registry row under BizFirstFiDB\...\dbo\Data\projects\{Category}\{Node}\ — often with its own NodeReport.md coverage matrix. Point to it. Use it. Don't redo it.
  2. Backend code. The real executor/domain/services project paths — and whether the node's own unit-test project, if it has one, actually still builds. (It's not guaranteed to — see the Elasticsearch example, where a real one didn't.)
  3. Feature/capability breakdown. One row per real operation the node routes on, each mapped to a specific Phase 1 test case.
  4. Credential sourcing. See the special instruction below — mandatory whenever the node needs a real external account to execute for real.

Two-phase testing, strictly sequenced

Prove each part alone before proving the whole

Phase 1

Isolated, one feature at a time

One trigger node wired straight into one instance of the node under test, configured for exactly one capability. Ten features, ten small workflows. Proves each one works on its own.

Phase 2

One combined, chained workflow

Built only after every Phase 1 case has a verdict. Chains every feature from Phase 1 into a single realistic sequence, executable end to end in one click.

Do not build or run Phase 2 in parallel with Phase 1, and do not skip straight to it. A combined workflow that fails tells you something failed — a workflow built feature-by-feature first tells you exactly which feature, because you already know the other nine work alone.

Building and running workflows: UI first, DB fallback only when needed

A node isn't an app, so "run the test" means "build a workflow" first

Chrome-driven, through Flow Studio's real UI, is the preferred and default method. Reach for a direct-DB build only when the real UI is genuinely unusable for the case at hand — a logged-out session you can't quickly re-authenticate, or a large batch of near-identical isolated Phase 1 cases where a DB build followed by a confirming UI pass is more practical than clicking through all of them by hand. It is never a first choice, and it never replaces the confirming UI pass a node still owes before sign-off.

  1. Preferred — Chrome-driven, through Flow Studio's real UI. Confirm the session is actually logged in before anything else (it can be silently logged out). Drag the node's real palette template onto the canvas, fill its Atlas Form with real values, wire a trigger into it, save, and execute via Flow Studio's own run/observer surface. The only path that proves the Atlas Form itself renders and accepts input correctly, and that a failure shows up legibly on the canvas.
  2. Fallback only — direct-DB build. Clone a known-good prior workflow's row shape (Process_Processes → ...Threads → ...ThreadVersions → ...Elements → ...Connections) via dynamic SQL keyed off INFORMATION_SCHEMA.COLUMNS, swap in the node's real config JSON, and read every row back to confirm it landed exactly as intended. Record explicitly in results.md why the fallback was used — the Elasticsearch pilot used it because the browser session was logged out at build time, not by default choice.

Executing a built workflow for real, either way, uses a genuinely proven endpoint (needed directly when using the DB fallback; Flow Studio's own UI calls the same thing under the hood):

POST https://localhost:10001/api/v1/process-engine/execution/execute-by-id
Authorization: Bearer {locally-minted JWT}

{"ProcessID": <id>, "AppID": 1}

Full recipe — where the signing key lives, the exact claim shape, the security caveat worth repeating to whoever reads it next — lives in elasticsearch\workflow-build\README.md. Reuse that recipe rather than re-deriving it per node.

Verifying against the real backend — required, not optional

A node's own "success" status is a claim, not evidence

Whichever build method was used, and even for a Phase 2 chain where one step reads back what an earlier step wrote, the node's own reported result is not sufficient evidence for any case that touches real external data — that only proves the node's calls agree with each other, not that either one is actually correct against the real system. For every write or query case, independently confirm against the external system's own interface:

  • Write case: after the node reports success, call the real backend's own API directly (for Elasticsearch: a plain curl with the same credentials) and confirm the record genuinely exists, field-by-field, matching what was written.
  • Query/search case: run the same query directly against the real backend and confirm its result matches what the workflow returned.

Record both the workflow's own output and the independent verification call's raw output side by side in results.md — a Pass requires both, not either alone. This is a standing requirement for every node type this framework tests, not specific to Elasticsearch.

Sourcing real test credentials

A standing instruction, for every node type — not a one-off workaround

Special instruction — from Binoy

An agent cannot create an account or enter payment details on the operator's behalf — that stays a human action. But "blocked, need credentials" is not a real answer for a junior operator either. Instead: find the real external service's free or trial tier, tell the operator exactly which account to create and where, have them open it in the Chrome extension once it's ready, and take it from there.

  1. Find the real free/trial tier. Check the vendor's actual current signup page yourself — terms change. Document what you found, dated, in the node's resource.md.
  2. Name the exact ask. Tell the operator, concretely: which URL to sign up at, and to open the resulting console in the Chrome tab this session is already using — a fresh tab, never one another concurrent agent might be mid-use on.
  3. Read the real values from the open session. Once the operator confirms it's open, the agent reads the endpoint/API key directly via claude-in-chrome — never by asking for a password to be pasted into chat.
  4. Configure and validate for real. Update the already-built workflow's config with the real values (an UPDATE, not a rebuild), execute it, capture the result.

Worked example: for Elasticsearch, this is Elastic Cloud's free 14-day trial — no credit card required to start, verified live against their own signup page, not assumed. See elasticsearch\resource.md §5 for the exact checklist this produced.

Certification & sign-off

What "done" actually means

A node is ready for sign-off only when every Phase 1 case, individually, and the Phase 2 combined case all show a real Pass — backed by real execution results and real screenshots for anything UI-facing — not a description of what should happen.

VerdictMeans
PassExecuted for real, expected result observed, evidence attached.
FailA real defect — evidence attached, reproducible.
BlockedCouldn't run yet — reason named explicitly. Never silent, never fabricated as a Pass to close the gap.

An honest, in-progress certification round — real Pass everywhere verifiable without live credentials, real Blocked-with-a-checklist everywhere else — is exactly what elasticsearch\testround\r1\results.md looks like today. That is the bar, not a finished state to imitate only once everything is green.
