Revised 2026-09-01 — the original design (automatic load, client-side filtering, no Search button) was rejected: "I dont like the design. We need pagination, an explicit search/reset button and also server side filter. this is enterprise system." This version reflects that direction. Backend capability now confirmed (§10): pagination is fully real and working today (total count, total pages, next/prev flags — no backend work needed); server-side filtering is confirmed not implemented anywhere in the call chain — a real, but small and precisely-scoped, backend fix (one file, DocumentRepository.cs) is required before this design's filter fields can do anything server-side. Pieces still marked unconfirmed (Reset button, dedicated pagination UI) remain best-guess, not yet read from real source.

3. End-to-end flow

1
Form opens — grid starts empty
No automatic fetch. Real UX departure from Document Manager's own "always show something" pattern — deliberate, per the enterprise-pattern requirement.
2
User fills filters, clicks Search
search-submit fires action-search-documents.
3
Filter values sent to the server
Confirmed no-op today — traced the full call chain to the shared BaseRepository.GetAllAsync; request.Filters is never read anywhere in it. The backend will silently return an unfiltered (but correctly paginated) page regardless of what's sent here, until DocumentRepository.GetAllAsync is overridden to apply them (§10 — one file, precedented pattern already used by that file's own GetByTypeAsync/GetByCategoryAsync).
4
Server returns one filtered, paginated page
Response maps into results-grid — blocked today: response-mapping only fires for the load trigger in real code, never submit (§5 Q3). Needs fixing before this works at all.
5
User changes page-number, clicks Search again
Re-runs the same action with an updated page parameter — a real dedicated pagination UI (Prev/Next, page picker) would be nicer than a raw number input, flagged as a follow-up.
6
User clicks Reset
search-reset's config.resetForm is an unconfirmed capability — needs verifying against real source before this button can be trusted to actually clear the filter fields.
7
User edits a row via the grid's built-in Edit button
Unchanged from v1 — targets real PUT /api/v1/documents/{id} with documentName / documentDescription / documentTypeID / documentCategoryID / classificationName.

4. Known gaps & blockers

Server-side filter support — confirmed not implemented (small, scoped fix identified)
Traced the full call chain to the shared BaseRepository.GetAllAsync — request.Filters is never read anywhere in it, platform-wide, not just for Documents. Concrete fix: override GetAllAsync in DocumentRepository.cs (one file) to read Filters["nameContains"/"documentTypeID"/"documentCategoryID"] and apply .Where() clauses, mirroring that same file's existing GetByTypeAsync/GetByCategoryAsync. No controller/service/DTO changes needed. A generic platform-wide fix in the shared BaseRepository was considered and deliberately not recommended (too much blast radius).
Response-mapping only wired for the load trigger
This design's move to submit makes this a hard blocker, not a footnote — search results cannot reach the grid until this is fixed.
Outgoing payloadMapping is applied backwards in the one real consumer
The Studio preview's request-building code inverts key/value from the confirmed authoring convention — filter values would not reach the backend correctly until this is fixed.
Form-Actions Player bug (still the base blocker)
The real deployed Player doesn't fire authored apiActions at all today, regardless of trigger. Fix designed, not yet implemented.
Auth not wired to apiActions calls
No real session JWT reaches any apiActions call today. 5-file build item, target contract auth: "passport" | "none".
Reset button and real pagination UI — unconfirmed capabilities
config.resetForm and any dedicated server-driven pagination control are best-guess designs, not read from real source. Need the same verification treatment as everything else before being trusted.
Foreign-key columns show raw IDs, not names
Unchanged from v1 — documentTypeID/documentCategoryID render as raw numeric IDs; no confirmed grid capability to resolve them to display names.
